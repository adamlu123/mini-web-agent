# Actor completion synthesis

## Bottom line

Actor can reach complete evaluator-visible native state most reliably on
bounded mechanical edits with known facts and readable final state. It is weak
on semantic ambiguity, session/path identity, and recognizing failed
exploration.

## Recurring successful sequence

1. Inspect initialized state and source assets.
2. Select the canonical parser-visible/native surface.
3. Apply the complete exact set/cardinality.
4. Use the application’s persistent workflow.
5. Reload/reopen and verify native state.
6. Submit only after readback is consistent.

Examples:

- Task 003: exact images, OOXML backgrounds, alpha, and render/readback.
- Task 028: native booking functions plus reload verification of four records.
- Task 091: native chart/OOXML construction materially improved score.

## Recurring failures

- **Incomplete native state:** task 011 created no workbook/Zotero deliverables.
- **No persistent completion:** task 048 never created a completed game save.
- **Wrong surface:** correct state in a replacement session is evaluator
  invisible.
- **Wrong path/filename/geometry:** already incorrect at Actor submission.
- **Unproductive persistence:** task 039 initially stopped before the complete
  dynamic inventory; a later complete-monitoring trajectory reached full score.

## Score-backed conclusions

- Actor is reliable at mechanical completion/readback, not hidden exact values
  or evaluator conventions.
- Construction success is not final-state proof.
- Exact surface identity—path, native object, cookie/session, serialization—is
  repeatedly score-facing.
- Actor self-ledger claims are not evidence.
- Fresh Verifier usually observes Actor failures rather than causing them.
- Productive persistence requires a concrete state signal and a changed route,
  as in task 095’s legitimate source recovery.
