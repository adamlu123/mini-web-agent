# CLI Harness Research Gates

## Purpose

The default remains baseline behavior `b091c78`.

Do not convert a plausible diagnosis, task-level improvement, correlation, or
aggregate subgroup movement into a harness implementation proposal.

The generalized and canonical-closure experiments demonstrated the failure
mode this gate prevents:

- several individually plausible mechanisms were bundled;
- schema and routing complexity grew before causal activation was proved;
- one-off task movements were described as promising levers;
- protection failures and ordinary Actor variance erased small gains;
- expensive panels established that the interventions did not cause the scored
  improvements.

## Language discipline

Before qualification, call an idea:

```text
unproven candidate
```

Do not call it:

```text
next lever
strongest lever
supported improvement
expected uplift
```

unless every implementation gate below passes.

## Mandatory pre-implementation gates

No behavioral code change or paid VM panel may be proposed unless:

1. **Three-task recurrence**
   - at least three independent exact selected attempts share the same first
     causal divergence;
   - evaluator-conflict, infrastructure, and domain-incapability cases do not
     count toward recurrence.

2. **Intervention timing**
   - the proposed mechanism acts before the score-changing artifact/state is
     created;
   - post-submit diagnosis, verification, or narration does not qualify.

3. **Offline counterfactual**
   - recorded traces show the intervention would change the concrete
     score-facing action or artifact on all qualifying tasks;
   - changing a prompt, report, plan, status, or self-description is
     insufficient.

4. **Historical control comparison**
   - compare each qualifying failure with a full-score control using the same
     mechanism;
   - state exactly what the control did differently.

5. **One mechanism**
   - one prompt rule, routing rule, role, schema, budget change, infrastructure
     change, or repair policy per experiment;
   - never bundle multiple unproven changes.

6. **Rejected-pattern check**
   - explicitly prove the proposal is not a renamed form of:
     - broad checklist;
     - Actor self-ledger;
     - generic Verifier repair;
     - evaluator emulation;
     - more calls alone;
     - late completion;
     - whole-binding probe locking;
     - proof-schema expansion;
     - file-only rollback presented as full safety;
     - post-submit closure.

7. **Complexity budget**
   - no new model role or structured schema without explicit user approval
     after the evidence packet is reviewed;
   - default implementation is one concise prompt/routing invariant;
   - if the mechanism requires multiple new statuses, arrays, scopes, or
     lifecycle branches, reject it before coding.

8. **Activation test**
   - define a runner-observable activation event before implementation;
   - model text, plans, ledgers, and pass/fail claims never count as activation.

9. **Protection-first design**
   - define full-score protections and stability controls before coding;
   - a protection regression rejects the implementation regardless of treatment
     aggregate.

10. **Repeated low-width evidence**
    - first VM test is a small matched panel at width no greater than 24;
    - qualifying treatments run multiple fresh-VM repeats per arm;
    - do not launch a broad or high-width panel to discover whether the
      mechanism activates.

## Required evidence packet

Before asking to implement, provide:

| Field | Requirement |
|---|---|
| Candidate name | Neutral, non-promotional |
| Three qualifying tasks | Exact selected directories |
| First causal divergence | One sentence and trace step per task |
| Full-score controls | Exact control directories and contrasting action |
| Score-facing state | Exact file/session/native field changed |
| Intervention timing | Before that state is created |
| Offline counterfactual | Concrete changed command/action |
| Rejected-pattern audit | Explicit comparison |
| Activation event | Runner/tool observable |
| Protections | Exact IDs and baseline scores |
| Repeats/concurrency | Low-width matched design |
| Kill condition | Predefined rejection rule |

If any field is absent, continue offline analysis or stop. Do not implement.
